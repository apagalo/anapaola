When the Reporting System Became the Problem

After three years of using data to support portfolio decisions, a new challenge emerged: how do you create one global view when different teams don't work in the same way?

Context

The reporting behind the case #1 didn't appear overnight.

It started around three years ago, when much of our operational analysis was still reactive: first a question came up, then information was pulled together in Excel, and an analysis was created for that particular need.

While working across Design teams, I started experimenting with Power BI to turn recurring questions into recurring visibility.

The Power BI reports became a recurring way to understand resources, portfolio, forecasts and budget and eventually enabled questions like the ones in the previous case.

The idea also continued outside my scope. After I moved areas, another product line built Power BI capability locally to continue the reporting approach that had started there.

For several years, it worked.

Then the organization evolved.

The New Problem

One organization. Different operating realities.

Today, creating global Design visibility means bringing together a much more heterogeneous environment.

Physical and Digital Design don't necessarily work in the same way. Even individual product lines can use different tools, workflows, project structures and data sources.

The reporting problem had changed. It was no longer simply:

How do we visualize the information?

It became:

How do we create one coherent global view when the teams behind it don't all operate in the same way?

The Diagnosis

My first instinct wasn't to add more dashboards.

I started looking at the system itself:

  • Where does the information live?
  • How do different teams actually work?
  • Which differences create unnecessary fragmentation?
  • What can reasonably be standardized?
  • And what needs to remain different?

That distinction matters.

Forcing every team into the same workflow just to simplify reporting could move the complexity from the report back onto the people doing the work.

So the principle I started working with became:

Standardize where it creates value. Connect where differences need to remain.

Exploring the Solution

That principle made APIs particularly interesting.

Instead of requiring information to be repeatedly moved and reshaped for reporting, APIs can connect to the systems where the work already happens and automate how that information flows into a common layer.

The architecture I'm exploring looks like this:

Different teams & workflows
↓
Different source systems
↓
APIs
↓
Automated data flows
↓
Common reporting layer
↓
Global portfolio visibility

The goal isn't to make every team work identically. It's to create enough common structure above those differences to understand the organization as a whole.

Building Beyond the Tools I Already Knew

There was another constraint: I knew what I wanted to explore, but I'm not a software engineer.

So I started using AI-assisted development to prototype and build, learning the technical pieces as the problem required them.

The API connection is now working and automated data flows are running. I'm currently developing the broader web-based reporting experience.

The system is still a work in progress.

And that's important: I'm not starting with a finished answer. I'm testing whether the architecture actually solves the problem before treating it as one.

The Next Question

Can we go beyond showing more data?

Connecting the information solves one layer of the problem.

But three years of working with reporting has made me increasingly interested in another one.

The most valuable moments haven't been when a dashboard showed us another number. They've been when a pattern made us ask a better question.

So the next area I'm exploring is whether AI can eventually help identify patterns, anomalies and questions worth investigating across a global portfolio — moving the system closer to:

Data
→
Visibility
→
Insight
→
Question
→
Decision

AI-supported analysis is a direction I'm exploring, not a finished capability.

What I Took From It

Don't fall in love with the tool.

Power BI was the right answer for the problem we had at the time. It served us for years and helped create the foundation for the decision-making in the previous case.

But organizations evolve, and eventually the question evolved with it.

I don't want the tools I already know to determine the solutions I'm willing to consider.

I want to understand the problem first, explore what the system actually needs, and then learn or build what is required to solve it.
